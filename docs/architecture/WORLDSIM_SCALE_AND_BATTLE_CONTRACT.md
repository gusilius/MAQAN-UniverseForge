# WorldSim: контракт масштабирования политики и массовых боёв

**Статус:** архитектурный контракт и план внедрения. Численные значения ниже — начальные бюджеты для измерения и настройки, не заявленные результаты тестов.

## 0. Неизменяемые правила

1. Не удалять механику, типы деятельности, население, государства, армии, исторические события или длительность симуляции ради производительности.
2. Не вводить глобальный потолок жителей/государств/отрядов и не урезать автономную кампанию. Ограничиваются только работа за один серверный тик, частота необязательных пересчётов и визуальная детализация.
3. Единственный источник истины остаётся в существующих доменных системах UniverseForge. Не создавать параллельные Character, Realm, Settlement, Army или финансовые реестры.
4. Любой реальный персонаж сохраняет стабильную идентичность. Когорта — сжатое представление состава и состояния, а не новая личность. При необходимости индивидуального появления/имени член когорты получает детерминированный стабильный ID и каноническую запись Character без смены UUID/истории.
5. Решение может выполняться параллельно только над неизменяемым снимком. Все изменения Minecraft, инвентаря, блоков, сущностей и авторитетных доменных реестров применяются на серверном потоке через существующие валидаторы и ActionExecutionService.
6. Любая очередь сохраняет работу, имеет метрики возраста/повторов/ошибок и переживает сохранение/перезапуск там, где операция влияет на канонический мир. Переполнение не может молча терять задачи.
7. Никакого изменения скорости/результата симуляции в зависимости от нагрузки: при нехватке бюджета работа переносится, а не отбрасывается. События, причинность, порядок применения и seed-детерминизм сохраняются.

## 1. Единый бюджет исполнения

Планировщик учитывает MSPT и распределяет бюджет в порядке приоритета:

1. непосредственное взаимодействие игрока, физический мир рядом и ближний бой;
2. активные отряды/операции и бои в загруженных областях;
3. важные политические решения и срочные события;
4. дальние бои и фоновые хозяйственные/демографические пересчёты;
5. аналитика, хроника, необязательные проекции интерфейса.

Бюджет — квота на работу за тик, не ограничитель количества объектов. Начальная гипотеза для политического планировщика — 1–2 ms/tick; значение должно подбираться профилем и не является гарантией. Остаток очереди переносится. Срочные события (смерть, наследование, смена титула, начало войны, брак, кризис) получают приоритетное пробуждение, но не нарушают последовательность доменных транзакций.

### Метрики

- длительность обработчика и фаз: count, total, max, p95, p99;
- thread CPU time отдельно от wall-clock;
- MSPT/p95/p99 и watchdog stack;
- размер очереди, самый старый элемент, throughput, retries, backoff, dead-letter/blocked;
- количество снимков, bytes in/out, serialization time;
- rejected/applied по типизированной причине и подсистеме;
- число активных когорт, физически materialized entities и видимых клиенту инстансов.

Нельзя подменять отсутствующую метрику нулём. Профиль должен указывать покрытие измерений.

## 2. Политика и высшие персонажи

### 2.1 Персональный LOD

- **LOD 0:** правитель, наследник, члены совета и персонажи с активным кризисом/решением. Полный набор допустимых решений и высокая частота.
- **LOD 1:** знать, командиры, придворные, дипломаты, главы организаций. Полная индивидуальная логика с более редким расписанием, смещённым стабильным hash от ID.
- **LOD 2:** остальные жители. Не запускать дорогой индивидуальный utility search каждый цикл; использовать агрегаты домохозяйств/профессий/поселений, потребности и детерминированные фоновые обновления. При наследовании, браке, заговоре, назначении, войне, личном взаимодействии или изменении статуса персонаж повышается и получает полный профиль.

LOD не меняет доступные игроку механики и не означает «не симулируется». Базовые потребности, родство, имущество, здоровье, возраст, смерть и наследование продолжают учитываться доменными системами.

### 2.2 Планирование и события

- Стабильное расписание: `hash(worldSeed, characterId) % interval`, а не синхронный запуск всех персонажей в один день.
- Колесо таймеров/приоритетная очередь следующего пересмотра; события могут разбудить субъекта раньше.
- Dirty flags/version counters на зависимости: если входы не изменились, не повторять дорогую оценку.
- Backoff для неуспешных/неизменившихся решений с причиной, числом повторов и временем следующей попытки.
- События наследования, брака, смерти, войны, смены титула, настроения и отношений инвалидируют только связанные кэши.

### 2.3 Rust decision engine

- На первом этапе оставить существующий JSON контракт и измерить его; не менять сериализацию одновременно с алгоритмом.
- Следом — versioned binary delta protocol: seed, world/day, base revision, changed realms/characters/settlements, stable numeric IDs, bounds, checksum и schema version. Полный snapshot остаётся bootstrap/recovery fallback.
- Строки и JSON — только на границе совместимости. Внутренние структуры — компактные numeric IDs/flags и adjacency layout, если профили подтвердят выигрыш.
- Общие realm aggregates (казна, армия, угрозы, стабильность, мнения) строятся один раз на revision и переиспользуются.
- Дешёвые masks/eligibility prefilter → utility только для top-K допустимых действий. K — измеряемая настройка, не ограничение функциональности: кандидаты обрабатываются следующими порциями.
- Параллельная read-only фаза допустима через Rayon после подтверждения thread safety; сортировка результатов и последовательный apply — стабильные по ID.
- JNI: ловить Rust panic на FFI-границе, не допускать unwinding через JVM ABI; ошибки возвращать типизированным результатом. Асинхронная двойная буферизация — отдельный этап с revision/fence, cancellation и backpressure, без блокировки server thread и без применения устаревшего snapshot.

### 2.4 Исторические персонажи

- Значимые персонажи и все те, кто влияет на действующие системы, остаются каноническими Character.
- Неактивные неименованные линии могут храниться компактно, но должны сохранять родословную, права, наследственные связи и возможность детерминированного восстановления.
- Неименованный участник когорты материализуется как Character при значимом событии; стабильный ID выводится из seed/formation/cohort/member slot и затем закрепляется. Нельзя создать вторую запись для уже существующего UUID.
- Архив — сжатие представления, не удаление истории или последствий.

## 3. Массовые бои и 1000×1000

### 3.1 Серверная модель

- Сервер симулирует когорты/подразделения и их состав, а не 2000 отдельных Minecraft living entities одновременно.
- Когорта сохраняет численность, классы/типы бойцов, оружие/броню, навыки/опыт, мораль, усталость, снабжение, потери, ранения, командную связь и стабильные ID состава.
- Военный шаг может идти с целевой частотой 4–5 Hz, независимо от 20 TPS, но время мира/бой не ускоряется и не теряет шаги: накопитель elapsed time и bounded work queue догоняют без изменения причинности.
- Пространственная сетка для ближайших целей; общее поле потока/путь на сторону и цель; formation slots вокруг командира. Персональный pathfinding — только когда нужен локальный физический бой/особое действие.
- Дальний бой — детерминированные залпы/области урона с сохранением оружия, дальности, укрытий, навыка и случайности от battle seed; настоящие снаряды создаются вблизи игрока или для значимых событий.
- Потери пишутся пакетно в военный журнал по когорте/событию; именные герои, офицеры, ветераны и участники личных событий получают индивидуальные записи. Казначейские проводки остаются корректными и не создаются искусственно на каждого рядового.

### 3.2 Три визуальных кольца

- **Ближнее:** ограниченный адаптивный пул настоящих Minecraft entities с полным физическим взаимодействием/AI для локального боя.
- **Среднее:** анимированные клиентские модели/puppets без server AI и навигации.
- **Дальнее:** клиентские instanced meshes/billboards, без отдельных Minecraft entities.
- Переходы между кольцами двусторонние и сохраняют battle/cohort/member identity, здоровье, мораль, позицию и потери. Итог ближнего боя возвращается в каноническую когорту один раз по transaction ID.
- Сервер отправляет только нужные игроку видимые состояния с quantized transforms/strength/morale, целевой частотой 2–5 Hz; клиент интерполирует. Сервер не принимает от клиента авторитетные потери/позиции.
- Adaptive quality использует измеренный MSPT/FPS и видимость. Снижается дальность/частота/визуальная детализация, а не численность, механика, точность результата или доступность команд.
- Renderer — отдельный экспериментальный модуль; проверить Embeddium/Sodium/Forge render lifecycle и fallback на обычный рендер. Не внедрять нестабильный renderer в основной боевой путь до compatibility tests.

### 3.3 Переходы и multiplayer

Каждая когорта имеет канонический roster identity/revision. Перевод члена между cohort, entity и Character — атомарная операция с idempotency key. Два клиента получают одно и то же состояние; визуальный seed не заменяет серверную авторитетность. При disconnect/reconnect, unload/reload chunk и server restart результат восстанавливается из сохранённой военной модели.

## 4. Сохранения и целостность

- Сегменты append-only событий с sequence ID, schema version и checksum.
- Дельты по revision вместо полной перезаписи всей истории при каждом checkpoint.
- Checkpoint coordinator фиксирует согласованную revision для казны, армий, поселений, персонажей и событий; manifest с hash/sequence и восстановлением после crash.
- Транзакции между системами используют prepare → commit → receipt/outbox; повтор идемпотентен. Не обрезать финансовую и историческую историю.
- Snapshot/segment compaction разрешена только при доказанной возможности восстановить точную историю и audit trail.

## 5. Порядок внедрения

1. Профилировщик и базовая линия на полном сервере; метрики покрытия и артефакты.
2. Очередь и пакетная материализация населения: стабильные UUID, Origins, progress cursor, bounded items/tick, persisted pending state, no silent overflow.
3. Планировщик персонажей LOD 0/1/2, hash scheduling, event wakeups, dirty versions, deterministic apply.
4. Бинарный versioned delta protocol как параллельный новый путь с JSON fallback; сравнение byte/time и parity на одинаковом seed.
5. Save/checkpoint coordinator, сегменты, дельты, восстановление между модулями.
6. Очереди AI/settlement/RTS: retry/backoff/cooldown/age/overflow metrics.
7. Серверный cohort battle prototype с детерминированными 1000×1000 tests.
8. Клиентские три кольца и instancing; совместимость рендереров и multiplayer.
9. Интеграционная кампания: экономика, снабжение, политика, армия, физический мир, история и обычный world regression.

## 6. Бюджеты и критерии качества

Начальные цели для экспериментов, не измеренные обещания:

- политика: ориентир 1–2 ms/tick в среднем для фонового slice; срочные задачи имеют отдельную очередь и не блокируют сервер.
- массовая тактика: ориентир 4–5 simulation steps/s при 1000×1000; пропускная способность и backlog фиксируются отдельно.
- видимое состояние: 2–5 network updates/s на видимые formation groups.
- ближние Minecraft entities: динамический пул, стартовая гипотеза 30–60 на игрока, адаптируется по MSPT; это не лимит бойцов в мире.
- CI: p95/p99 и backlog growth должны оцениваться на сопоставимых seeds/fixtures и Windows x64 Forge; пороги утверждаются после baseline. Любой тест также проверяет идентичность, сохранение, баланс и полную функциональность.

## 7. Что считается регрессией

- потерянный житель/боец, изменённый UUID, двойной Character, исчезнувший наследник/инвентарь/имущество;
- непроигранное событие или неучтённые потери/снабжение;
- отличие результатов при одинаковом seed и версии протокола;
- молчаливое удаление/переполнение очереди;
- отсутствие физического результата в Minecraft при наличии результата только в абстрактной модели;
- нагрузка скрыта путём отключения механик, сокращения населения или уменьшения продолжительности кампании.

Любая оптимизация должна пройти parity tests, save/reload, ordinary world regression и полную интеграционную кампанию.

## 8. Масштабирование от одиночного мира до больших серверов

### 8.1 Без искусственного потолка и без обещания бесконечного железа

- Не вводить глобальные caps на Characters, realms, settlements, armies, cohorts, history duration или число игроков как способ скрыть нагрузку.
- Физические ресурсы конечны. При исчерпании вычислительного бюджета система обязана сохранять pending work и причинный порядок, а не удалять сущности, пропускать годы, сокращать механику или незаметно менять результат.
- Backpressure ограничивает только число одновременно исполняемых задач/объём работы за slice; очередь должна быть сохраняемой, наблюдаемой и возобновляемой. Нельзя заменять bounded execution unbounded in-memory queue.
- LOD и cohort compression меняют частоту/представление исполнения, но не каноническую идентичность, доступные действия, последствия, историю или итоговую симуляцию.

### 8.2 Профили развёртывания

1. **Single-player / integrated server:** один авторитетный world owner; Rust worker pool обрабатывает immutable snapshots, Java/Minecraft server thread применяет эффекты.
2. **Co-op / dedicated server:** тот же авторитетный сервер для общего мира; клиентам не передаётся право вычислять/подтверждать канонические изменения. Игроки не создают отдельные копии государства/населения.
3. **Large server, one authoritative world process:** вычисления разбиваются на независимые read-only partitions (например, world/region/domain slices), затем результаты детерминированно сводятся и применяются по stable IDs на серверном потоке. Общие зависимости (казна, торговые сети, дипломатия, наследование, армейское снабжение) требуют явных cross-partition barriers и не могут независимо пересчитываться в каждом shard.
4. **Multi-process / horizontal scale:** будущий этап, не текущая возможность. Нужны явное владение регионами/доменами, leases и fencing epochs, durable messaging/outbox, согласованные checkpoint manifests, маршрутизация cross-shard действий, миграция ownership и recovery после потери узла. Один Minecraft Level/Entity не может одновременно иметь двух авторитетных владельцев.

### 8.3 Ограничение текущей реализации

Текущий `WorldSimComputeScheduler` — single-flight worker с одним native compute lease. Это безопасная стартовая архитектура для проверки асинхронной границы, но не доказательство горизонтального масштабирования и не конечная модель throughput для крупного сервера. Не увеличивать число потоков до завершения WF-RT-0023 и WF-RT-0021: сначала должны быть snapshot revision fences, детерминированное partition/reduce и durable apply receipts. Иначе параллелизм ускорит конфликтующие записи, а не симуляцию.

### 8.4 Критерии масштабирования

- нагрузочные профили на одинаковых seeds и версиях схемы; p50/p95/p99, MSPT, CPU time, queue age/backlog slope, memory/allocations, serialization bytes, recovery time;
- рост населения/государств/армий без искусственного caps и без потери полной механики;
- детерминированность при разных worker counts и разбиениях partitions;
- отсутствие starvation: старые задачи имеют измеряемый возраст и гарантированный прогресс;
- multiplayer: один канонический результат для всех клиентов, reconnect/restart/unload recovery;
- при переходе к нескольким процессам — тесты split-brain, lease expiry, ownership migration, delayed/replayed messages и crash between prepare/commit.
