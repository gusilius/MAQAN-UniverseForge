# Multi-planet runtime — implementation baseline from workflow run #2335

**Baseline commit:** `4a81f599e4a5e069999db7987045e88f3ce496e9`  
**Workflow:** `.github/workflows/universeforge.yml`  
**Runtime:** Minecraft 1.20.1 / Forge 47.3.0 / Windows x64

This document records the existing implementation and the next acceptance target. It is not a claim that two-planet travel or cross-dimension identity transfer is complete.

## 1. What already exists at this baseline

### Physical dimensions and terrain

- The normal Minecraft Overworld is generated by the vanilla generator.
- WorldForge registers the `worldforge:image` ChunkGenerator codec and matching biome source.
- A world-local datapack creates a dimension such as `worldforge:real-map`, with dimension type `worldforge:mapworld` and generator `worldforge:image`.
- The map generator samples the imported `.worldmap` package (`height16.png`, biome and river data) to create physical Minecraft chunks.
- The image-map acceptance setup creates that datapack in the same save's `world/datapacks`; it does not replace the vanilla Overworld.

Therefore the image-map server configuration already has the correct physical shape for the first two planets: **vanilla Overworld + mapped WorldForge dimension, in one Minecraft server process and one save**. The workflow also launches a separate vanilla-only server as an independent regression test; that second launch is not the architecture for multi-planet gameplay.

### World simulation and identity

- WorldForge establishes a save-level `WorldId`.
- WorldSim observes loaded chunks through `VanillaWorldGeography`, retaining dimension identity in its region keys.
- The image-map bootstrap sanitizes the imported package: it keeps geography, province/region hierarchy and settlement candidate sites, while removing pre-authored realm ownership and identity so the live political/identity systems can establish those.
- Settlement bootstrap logs show map-first anchors staged in `worldforge:real-map`; run #2335's artifact records 195 named settlement anchors and idempotent Colony record creation.
- The common addons (people, origins, realms, settlement, Genesis, trade, court, WorldSim, etc.) are built once and copied into the same server's mod folder.

## 2. What run #2335 actually proved

The workflow successfully:
- built the Rust WorldSim native engine and staged its Windows DLL;
- built WorldForge core and all addons;
- generated and validated a real `.worldmap` from repository `map.png`;
- started the vanilla-only server to the Forge `Done` marker;
- started the image-map server to the Forge `Done` marker;
- imported the map blueprint and staged 195 settlement anchors.

It did **not** pass its acceptance job. Both smoke script invocations exited with code 9 because the script tested the literal escaped text `${WF_ACCEPTANCE_MODE:-}` rather than expanding the environment variable. Consequently the smoke command block was skipped, the EXIT trap stopped the servers, and the diagnostics were recorded as `failed_unclassified`. The image-map log excerpt also does not prove that a chunk in `worldforge:real-map` was force-loaded and generated.

Do not report run #2335 as a successful two-world acceptance.

## 3. Immediate correction and acceptance target

The follow-up branch `feature/two-planet-runtime-from-2335` is based directly on the run's head commit. It:
- fixes the smoke-mode environment-variable expansion;
- keeps the ordinary-world smoke campaign-free;
- sends a live command into `worldforge:<map-id>`;
- force-loads a mapped-dimension chunk while the vanilla Overworld remains in the same server;
- checks a server-log marker proving that the running server resolved the mapped dimension before reporting mapped-dimension smoke success.

Acceptance must verify both:
1. vanilla Overworld loads normally;
2. the map dimension is registered, its chunk generator is invoked for a real chunk, and its data is saved in the same server process.

A passing script alone is still not a substitute for checking the actual dimension's chunk-generation log evidence and a restart/reload of the same save.

## 4. Intended planet model

- Planet A: the existing map-backed dimension. Keep map scale, landmarks, terrain and geography.
- Planet B: the vanilla Overworld dimension. Keep normal Minecraft terrain generation.
- Both belong to one universe and share the same installed mods, save root, WorldId, global Character authority, world clock, political/economic registries and simulation services.
- Planet/dimension identity must be stable and persisted. Dimension-local chunk coordinates and physical entity projections remain local.
- A Character moving between planets keeps the same canonical UUID, family, inventory, skills, property and relationships. Physical transfer needs a durable transaction/recovery contract; do not clone canonical Characters.
- A third space/orbit dimension is optional and later; do not block the first two planets on it.

## 5. Shared CK3-scale Genesis

Use one pipeline for both dimensions:
1. obtain terrain from that planet's configured provider;
2. derive a common geographic representation from the actual terrain;
3. build province and region geometry;
4. create settlement sites and named settlements;
5. generate inhabitants, races/ancestries, cultures and names from installed data;
6. generate political formations from supported mod definitions and simulation rules;
7. establish borders, rulers, houses, dynasties and relations;
8. publish the strategic map and snapshots to Atlas/MAQAN UI.

Only terrain acquisition differs. Do not copy image-authored political ownership into the live world. Do not inject campaigns, scripted objectives, forced rulers, or player progression conditions. Political history should emerge from simulation.

## 6. Work sequence

A. Finish the run-2335 smoke fix and prove both dimensions in one server/save.  
B. Add a save-backed PlanetId ↔ DimensionKey registry, with migration for existing saves and no silent rebinding.  
C. Ensure WorldSim, settlement, army, NPC, geography and simulation-LOD consumers iterate all configured ServerLevels while preserving dimension-local coordinates.  
D. Run the same Genesis pipeline independently against each planet's terrain provider, with idempotent durable stage receipts.  
E. Add crash-safe cross-dimension player/Character transfer and restart recovery.  
F. Publish the shared planet registry and each planet's strategic map to Atlas.

## 7. Non-goals for the first milestone

- Separate Minecraft servers or separate mod installations per planet.
- Campaign/scenario creation.
- Replacing the vanilla Overworld with the map.
- Duplicating WorldForge/WorldSim registries per dimension.
- Introducing a third space dimension before the first two pass.
- Claiming full CK3-scale generation merely because server startup and map import pass.
