# MAQAN RTS — единый командный слой и масштабирование боя

**Статус:** целевая архитектура и контракт дальнейшей реализации. Наличие описанного поведения в документе не означает, что оно уже подключено в игровом runtime.

## Цель

Объединить точное управление отдельным бойцом и массовое командование крупными армиями в одном RTS workspace MAQAN. Это не два режима с разными наборами сущностей: игрок управляет одной и той же иерархией на разной глубине.

- Тактический масштаб: отдельный Character/Troop, способности, экипировка, цель, позиция и состояние.
- Отрядный масштаб: выделение рамкой, группы, очередь приказов, строй, стойка, роли и локальный командир.
- Оперативный масштаб: взводы/батальоны и корпуса, направления, фланги, резервы, поддержка и снабжение.
- Стратегический масштаб: армия, кампания, театр военных действий, снабжение, потери и цели войны.

## Единый источник истины

- Canonical Character UUID остаётся идентичностью бойца; смена роли, подразделения или режима управления не создаёт нового персонажа.
- `Squads` владеет физическими тактическими отрядами и очередями приказов.
- `ArmyHierarchy` связывает стратегическую армию → корпуса → существующие squad IDs.
- `CommandDelegation` задаёт только полномочия. Она не является вторым хранилищем состава, приказов, личности или ИИ.
- Существующие `Formations`, `TroopController`, `Leadership`, `ArmyLink` и боевые расчёты переиспользуются. Нельзя создавать параллельные формации, реестр Characters или планировщик.

## Иерархия полномочий

При разрешении полномочий используется ближайшая явно заданная политика:

1. Squad override.
2. Corps policy.
3. Army policy.
4. Если ничего не задано — PLAYER_DIRECT.

Явный PLAYER_DIRECT на более низком уровне блокирует наследование ИИ сверху. Игрок может немедленно вернуть себе отряд; после отдельной команды снятия override подразделение снова наследует политику корпуса/армии.

- PLAYER_DIRECT: ИИ исполняет приказ игрока, но не меняет цель/задачу. Может предоставлять рекомендации.
- DELEGATED: Character-командир принимает ограниченные тактические решения внутри заданной цели, радиуса ответственности и разрешённых действий.
- AUTONOMOUS: больше свободы в рамках выданной политики; не означает безграничную власть.

Права на engagement, pursuit, retreat и смену objective проверяются сервером. Сам факт назначения Character командиром не даёт ему права управлять чужими подразделениями.

## UI: один workspace, несколько масштабов

Центральная область остаётся игровым полем/картой и не закрывается панелями специалистов. Выбор бойца или группы обновляет компактный инспектор, но не раскрывает дополнительные панели автоматически.

- Главный selection strip: количество, состав, среднее состояние/мораль, текущий приказ и командир.
- Контекстная command palette: действия, допустимые для текущего типа выделения; без длинных текстовых кнопок.
- Специальные иконки раскрывают компактные плавающие панели: способности, строй, роли, командование, снабжение. Панели двигаются независимо; весь shell не перетаскивается.
- Army/Corps tree открывается по явному действию и позволяет выбирать уровень командования без потери текущего игрового контекста.
- Любая команда должна показывать получателя, цель, очередь/немедленное исполнение и причину отказа.
- Контрольные группы 1–9 и индивидуальный выбор остаются доступными одновременно с выбором корпуса/армии.
- First-person и top-down/isometric/strategic camera — представления одного состояния выбора и приказов, а не независимые симуляции.

## Масштабирование симуляции

Точность управления не требует материализовать каждого солдата как активную Minecraft entity на всём театре войны.

- Ближний/видимый бой: физические TroopEntity, индивидуальные Character, точное позиционирование и штатный Minecraft combat.
- Средняя дистанция: агрегированные отряды с сохранением состава, ролей, морали, снабжения и результатов боевых шагов.
- Дальний/неактивный регион: стратегические агрегаты армии и корпуса; переходы между уровнями должны быть детерминированными и сохранять Character roster/потери.
- Изменение детализации не должно дублировать солдат или повторно учитывать потери. Deployment, casualties, retreat, split/merge и demobilization должны быть идемпотентными переходами.

## Граница Java / Rust

Java собирает ограниченный immutable snapshot с revision: состав/роли, приказ и цель, commander Character ID и его доступные командные параметры, мораль/снабжение, видимые угрозы, локальные условия и эффективная политика полномочий.

Rust возвращает детерминированное предложение: действие, строй/позиции или целевую область, приоритет, причину, confidence и revision. Rust не читает/меняет Minecraft entities и не является источником прав командования.

Java повторно проверяет revision, владение, полномочия, цель и допустимость приказа, затем применяет решение через существующие `Squads` / `TroopController`. Устаревший snapshot отбрасывается. Используется существующий compute runtime/scheduler; второй бесконечный цикл или очередь не создаётся.

## Этапы интеграции

1. Хранение и разрешение наследуемых полномочий Army/Corps/Squad.
2. Компактный UI управления полномочиями и отображение effective mode; без автоматического раскрытия панелей.
3. Серверная проверка приказов и мгновенный player reclaim.
4. Tactical snapshot/proposal через существующий Rust compute bridge и revision guards.
5. ИИ-командир распределяет задачи вниз по иерархии; игрок может смешивать ручное, делегированное и автономное управление.
6. Профили характера/навыков командиров влияют на оценку риска и предпочтения, но никогда не обходят выданные полномочия.
7. Масштабные стресс-тесты после отдельного разрешения; до этого — точечные unit/build проверки.

## Критерии приёмки

- Не назначенные игроком отряды остаются PLAYER_DIRECT.
- Делегирование корпуса не перехватывает явно оставленные игроком отряды.
- Squad direct override блокирует родительскую политику; reclaim действует немедленно.
- Неверный командир, чужой владелец, запрещённый приказ и stale revision отвергаются.
- Save/load сохраняет иерархию полномочий без потери старых squad-only данных.
- Переключение камеры и детализации не меняет Character UUID, состав, имущество и учёт потерь.
- Выбор отдельного бойца остаётся возможным даже при существовании армии из тысяч стратегических солдат.

## Текущий интерфейсный проход (реализуемая часть)

- В компактной панели выбранного отряда доступны три явных действия: «Лично», «Делег.» и «Авто». Панель остаётся плавающей, перемещаемой и ограниченной игровым viewport.
- Политика отряда отправляется серверной командой и проходит проверку владельца. Для делегирования/автономности нужен назначенный командир — живой canonical Character, состоящий в этом отряде и совпадающий с назначенным squad leader.
- Политики армии и корпуса доступны через серверные команды `/wftroops command army <id> <direct|delegated|autonomous>` и `/wftroops command corps <id> <direct|delegated|autonomous>`. Для не-direct режима должен быть заранее назначен живой командир армии/корпуса.
- Эти команды записываются через общий ActionExecutionService и общий durable military snapshot transaction; отдельного второго механизма сохранения нет.
- Клиентская панель пока отправляет команды и не отображает подтверждённый effective mode из сервера. Следующий интерфейсный шаг — получить серверное состояние политики и показывать наследование/командира без локальных догадок.
