# MAQAN UniverseForge — Rust Compute Migration & Optimization Contract

**Статус:** обязательное архитектурное решение и рабочий план миграции  
**Активный репозиторий:** `gusilius/MAQAN-UniverseForge`  
**Рабочая ветка:** `feature/autonomous-world-simulation-engine`  
**Главная цель:** перенести тяжёлые детерминированные вычисления UniverseForge в Rust, устранить повторные вычисления в Java и Rust, согласовать оптимизации между всеми установленными модами и сохранить полную игровую семантику.

Этот документ — долговременная точка отсчёта для следующих чатов и изменений. Если старые документы описывают Rust только как необязательное ускорение или допускают постоянное параллельное исполнение одинаковой логики в Java и Rust, этот контракт уточняет и заменяет такие положения для целевой архитектуры. Переход выполняется постепенно, без одномоментного переписывания проекта.

---

## 1. Архитектурное решение

Целевое направление — **Rust Compute-First, Java/Minecraft Execution Layer**.

- **Rust** становится основным исполнителем тяжёлых детерминированных расчётов UniverseForge: симуляции населения и домохозяйств, экономики, производства, торговли, логистики, стратегического ИИ, политики, демографии, военного планирования, массовых боёв, анализа маршрутов и других вычислительных задач после аудита.
- **Java** остаётся адаптером к Minecraft/Forge и существующим игровым доменным API: жизненный цикл модов, события Forge, Entity/Block/BlockEntity, чанки, инвентари/NBT, физические изменения мира, сетевые пакеты, клиентский рендеринг, совместимость модов и безопасное применение результатов.
- **Rust не обращается к Minecraft API и не управляет Minecraft-объектами.** Он получает неизменяемые данные и возвращает результаты/команды с версиями и идентификаторами.
- **Java не должна продолжать выполнять ту же тяжёлую формулу параллельно с Rust после завершения миграции.** Java может проверять инварианты, валидировать права/состояние, применять изменения и поддерживать временный fallback, но не дублировать основной расчёт.
- Существующие системы, данные, механики, UUID, история и сохранения не заменяются упрощёнными аналогами.

Это не означает «переписать весь Java-код на Rust». Переносится вычислительная ответственность, а не Minecraft-интеграция.

## 2. Неприкосновенные правила

1. Не удалять механику, типы деятельности, население, государства, армии, исторические события, длительность симуляции или доступные игроку действия ради производительности.
2. Не создавать второй Character/Worker/Troop, Realm, Settlement, Army, Treasury, EventLog или иной канонический реестр.
3. Не допускать двух активных исполнителей одной и той же доменной операции. Для каждой операции в каждый момент должен быть один назначенный владелец вычисления.
4. Не выполнять один расчёт сначала в Rust, а затем повторно в Java «для надёжности». Для проверки эквивалентности допускается отдельный тестовый/теневой прогон на изолированном снимке, который не применяет побочные эффекты и выключен в обычной игре.
5. Сохранять UUID, родство, владение, инвентарь, профессию, навыки, историю, наследование и идентификаторы событий при смене роли, миграции, смерти и восстановлении.
6. Все изменения Minecraft и авторитетных Java-доменов применяются на серверном потоке через существующие API, валидаторы, транзакции и ActionExecutionService.
7. Параллелить только независимые вычисления над неизменяемыми снимками. Порядок результатов и применение должны быть детерминированными.
8. Ограничивать объём работы за тик, но не полный объём работы мира. Необработанная работа переносится на следующие циклы, а не выбрасывается.
9. Очереди должны иметь bounded memory, backpressure, приоритеты, возраст, retry, наблюдаемость и сохранение прогресса для важных операций. Переполнение никогда не теряет задачи молча.
10. Один seed + одинаковая версия правил + одинаковые входные события должны давать воспроизводимый результат независимо от расписания потоков.
11. Оптимизация не должна скрывать проблему отключением подсистемы, сокращением населения, урезанием истории или снижением качества симуляции.
12. Любая оптимизация проходит аудит пересечений с другими модами до включения.

### Каноническая идентичность

Rust может хранить компактное вычислительное представление Character/Realm/Army, но оно не является новым источником идентичности. Каждый объект связывается со стабильным каноническим ID и revision. Java-реестры и существующие доменные сервисы остаются точкой применения/проверки игровых фактов до тех пор, пока отдельное миграционное решение явно не изменит владельца сохранённого состояния.

Компактная когорта — это LOD-представление состава, а не новая личность. При материализации/дематериализации UUID, родство, владение, опыт, инвентарь, история и состояние должны сохраняться.

## 4. Главная проблема, которую нельзя допустить: двойное вычисление

Для каждой переносимой операции вести реестр владельцев (Compute Ownership Registry). Минимальные поля:

- стабильный ключ операции и доменная область;
- текущий исполнитель: Java legacy / Rust / внешний мод / общий Minecraft API;
- целевой исполнитель;
- входная schema version и revision;
- точка применения результата;
- старый код/метод, который должен быть отключён или превращён в adapter после cutover;
- тест parity, критерий переключения и возможность безопасного rollback;
- известные пересечения с другими модами.

### Правило миграции одной операции

1. Найти все места, где операция выполняется: tick handlers, event listeners, scheduled tasks, callbacks, mixins/coremods, Rust entry points и сторонние моды.
2. Определить одного текущего владельца и измерить стоимость/частоту.
3. Зафиксировать входы, выходы, порядок событий, побочные эффекты и инварианты.
4. Реализовать Rust-эквивалент как чистую функцию/задачу над снимком.
5. Сравнить Java и Rust на одинаковых fixtures/seeds в тестовом режиме. Теневой прогон не применяет изменения и не публикует события.
6. После parity переключить production ownership на Rust одним контролируемым cutover.
7. Старый Java-расчёт удалить из production path или оставить только тонкий adapter/валидатор. Не оставлять обе реализации активными.
8. Проверить save/reload, idempotence, event ordering, multiplayer и обычный мир.
9. Зафиксировать миграцию в реестре владельцев и в KNOWN_ISSUES/тестовом отчёте.

Fallback — это взаимоисключающий режим на операцию: либо Rust, либо Java fallback. Он не запускается одновременно с Rust для одного и того же входного revision. При переключении исполнитель и revision явно фиксируются в диагностике.

## 5. Не допускать конфликтов и бессмысленного дублирования оптимизаций между модами

Оптимизация всего проекта — это не набор независимых «ускорителей», которые каждый мод запускает поверх остальных. До внедрения нужно составить **Mod Optimization & Compatibility Inventory**.

Для каждого установленного/подключаемого мода зафиксировать:

- какие игровые циклы, события и данные он обрабатывает;
- какие операции он уже оптимизирует;
- какие mixins/coremods/ASM hooks он использует;
- какие очереди, executor pools, кэши, индексы и thread pools создаёт;
- какие chunk generation/loading/I/O/rendering этапы меняет;
- какие API/события предоставляет для интеграции;
- какие версии Minecraft, Forge/NeoForge и другие зависимости поддерживает;
- пересечения с оптимизациями UniverseForge и режим совместимости.

### Примеры обязательной проверки

- Если другой мод уже параллелит chunk generation/loading/I/O (например, C2ME в совместимой среде), UniverseForge не должен поверх того же участка запускать второй независимый параллельный scheduler без доказанной необходимости и тестов безопасности.
- Если мод оптимизирует block/entity tick или pathfinding, сначала проверить, не дублирует ли UniverseForge тот же индекс, кэш или повторное планирование.
- Если renderer вроде Sodium/Embeddium меняет клиентский рендер, серверная симуляция UniverseForge не должна вмешиваться в его внутренний render pipeline без отдельного совместимого адаптера.
- Если Lithium или другой оптимизатор устраняет лишнюю работу ванильного алгоритма, UniverseForge не должен повторно «оптимизировать» тот же алгоритм через конфликтующий mixin/coremod.
- Наличие стороннего оптимизатора не означает, что все его функции доступны на Forge/текущей версии. Совместимость проверять по фактическому loader/version и установленному набору модов.

### Политика интеграции

1. Предпочитать официальные API, события и capability detection вместо mixin-инъекций.
2. Для каждого оптимизируемого участка назначать одного владельца: Minecraft/Forge, сторонний оптимизатор или UniverseForge.
3. Если сторонний мод уже выполняет ту же оптимизацию, использовать его результат/контракт либо отключать только нашу дублирующую оптимизацию, сохраняя все игровые функции UniverseForge.
4. Не создавать второй глобальный thread pool, если можно использовать один контролируемый scheduler для задач UniverseForge. Не захватывать чужой executor без документированного API.
5. Кэши должны иметь единого владельца, правила инвалидирования, revision и метрики hit/miss. Два кэша одной информации допустимы только при разных назначениях и доказанной выгоде.
6. Не изменять внутренности стороннего мода и не отключать его функции без доказательства конфликта и отдельного решения.
7. При неизвестной совместимости — безопасный fallback и явная диагностика, а не молчаливое двойное исполнение.

## 6. Исполнительная архитектура Rust

### 6.1 Поток данных

1. Java на серверном потоке собирает согласованный immutable snapshot с revision.
2. Snapshot передаётся Rust через версионированный bounded ABI.
3. Rust scheduler ставит работу в очередь с приоритетом и дедлайном/бюджетом обработки.
4. Worker threads считают только независимые данные; не обращаются к Minecraft, Java Entity, Forge registries или Level.
5. Результат содержит operation ID, input revision, schema version, sequence и типизированные deltas/proposals.
6. Java забирает готовый результат позже на серверном потоке.
7. Java проверяет revision, идемпотентность, права, receipt и доменные инварианты.
8. Существующие ActionExecutionService/доменные API применяют изменения.
9. Подтверждённые события и receipts возвращаются в следующее вычислительное состояние.
10. Сохранение фиксирует согласованную позицию очередей/прогресса и состояние транзакций.

### 6.2 Очереди и планирование

- Приоритеты: непосредственные действия игрока/ближний физический мир; активные бои и операции; срочные политические события; фоновые симуляции; необязательные аналитические/UI-проекции.
- Квота ограничивает миллисекунды/объём работы за тик, а не численность мира и не полноту симуляции.
- Очереди имеют bounded memory, backpressure, fair scheduling, starvation protection, retry/backoff и возраст задач.
- Важные задачи имеют persisted cursor/checkpoint и идемпотентный transaction ID.
- Устаревший результат нельзя применять к новой revision; его нужно безопасно отклонить и пересчитать.
- При shutdown — остановить приём новой работы, завершить/сохранить безопасные checkpoints, затем закрыть worker pool.
- Отмена задачи допустима только если она не теряет уже зафиксированные события/побочные эффекты.

### 6.3 JNI и протокол

Текущий JSON/JNI путь сначала профилируется и остаётся рабочим compatibility path. Затем вводится versioned binary protocol/DirectByteBuffer или другой измеренно эффективный ABI.

Протокол обязан иметь:
- schema version и capability negotiation;
- world/operation ID, seed, sequence и base revision;
- стабильные entity IDs;
- единицы измерения и fixed-point precision там, где нужна детерминированность;
- размеры/лимиты, checksum и валидацию;
- typed errors и безопасную обработку panic на FFI boundary;
- backward-compatible save migration;
- JSON/bootstrap fallback на время миграции.

Нельзя одновременно менять алгоритм, формат протокола и владельца состояния без отдельных parity gates. Сначала отделить изменение исполнения от изменения представления данных.

## 7. Постепенная и незаметная материализация мира

Генерация и создание физических объектов должны быть незаметными для игрока, но не урезанными.

- Rust заранее планирует необходимые сущности/работы из seed и состояния мира.
- Java создаёт физические объекты небольшими порциями в безопасных точках server tick.
- Приоритет: рядом с игроком и активными игровыми событиями — выше; удалённые территории продолжают жить в агрегированной/фоново вычисляемой форме.
- Персонажи, Origins, семьи, поселения, постройки, ресурсы, блоки и визуальные проекции имеют независимые очереди, но согласованные IDs/revisions и зависимости.
- Материализация идемпотентна: повтор задачи не создаёт второго Character, Origins record, дома, блока или события.
- Сохраняются cursor, total/complete counts, retry reason, oldest task age и очередь отложенных работ.
- Очередь не должна терять задачу при достижении бюджета. Нужны backpressure и перенос на следующий тик.
- Не выполнять повторную полную проверку всех уже материализованных персонажей каждый цикл, если есть надёжная revision/index/dirty marker.
- При уменьшении численности в стратегической модели нельзя автоматически убивать канонических жителей. Смерть — только через доменную life/death simulation.
- Физический мир и стратегическая модель двусторонне сверяются: абстрактное поселение без физического отражения и физическая деревня без участия в общей симуляции — оба считаются дефектом.

## 8. Текущий аудит: подтверждённые факты и открытые риски

Срез по ветке на 2026-11-14, commit `8a4e48d235dea719d7b98f78638033f6467ea26b`. Это состояние на момент записи, а не гарантия, что последующие коммиты его не изменили.

### Уже существует

- Rust crate `mods/worldforge/native/worldforge-worldsim`.
- JNI entry points для `nativeDecide`, `nativeGenerate`, `nativeAdvanceEmergence`.
- Детерминированные тесты нативного ядра.
- Java adapter `NativeWorldSimulation`.
- WorldSim snapshot, proposal validation/application, ActionExecutionService integration и save flow.
- `EmergentPopulationIndex` поверх canonical CharacterRegistry — индекс, не второй реестр идентичностей.
- `WorldSimProfiler` с bounded ring buffer.
- Deferred chunk work в `VanillaVillageAdapter`.
- `docs/testing/KNOWN_ISSUES.md` с историей подтверждённых проблем и критериями закрытия.

### Подтверждённые ограничения

1. В `WorldSimMod.processServerTick` вызовы `NativeWorldSimulation.advanceEmergence(...)` и `NativeWorldSimulation.decide(...)` происходят синхронно в server tick handler.
2. JNI читает Java byte arrays, парсит JSON через Serde, считает и сериализует JSON в том же потоке вызова. Это создаёт копирование и блокирующее ожидание.
3. `syncEmergentPeople` синхронно создаёт недостающих жителей циклом до целевой численности и проверяет/создаёт Origins records для жителей. Это основной приоритет для инкрементальной материализации.
4. Rust `emergence::advance` может последовательно догонять годы до target year (в коде присутствует catch-up cap). Большой период нельзя выполнять одним длинным вызовом на server thread.
5. Текущий WorldSimProfiler измеряет только часть WorldSim server tick path; он не покрывает автоматически все обработчики всех аддонов.
6. Полная сериализация финансовой истории уже имеет streaming save путь; историю нельзя обрезать. Дальнейшие изменения должны сохранить бухгалтерские инварианты и транзакционную согласованность.
7. Сохранение Character может включать несколько связанных реестров. Нельзя заменять транзакционный persistAllRegistries на частичную запись без эквивалентной гарантии.
8. В KNOWN_ISSUES остаются открытые проблемы кампании, включая Watchdog/материализацию и производительность доменных проходов. Закрытие — только после повторного сценария и обычного мира.

## 9. Профилирование и доказательство эффективности

Перед изменением каждого участка фиксировать baseline и покрытие измерений.

Минимальные метрики:
- MSPT p50/p95/p99, max и watchdog/thread dump;
- wall-clock и thread CPU отдельно;
- длительность snapshot, encode/decode, JNI, Rust compute, queue wait, Java apply и save;
- queue depth, throughput, oldest age, retries, blocked/dead-letter;
- bytes in/out, allocations, GC pauses, heap/native memory;
- число обработанных сущностей и незавершённый backlog;
- applied/rejected с типизированной причиной;
- время загрузки/сохранения и восстановления.

Сравнивать одинаковые seed, world fixtures, версию правил и набор событий. Отдельно измерять:
1. чистый алгоритм;
2. передачу данных через JNI;
3. полную интеграцию на сервере;
4. обычный мир;
5. длительную автономную кампанию.

Нельзя объявлять оптимизацию успешной только по микробенчмарку Rust, если end-to-end server tick не улучшился.

## 10. План реализации — без параллельного переписывания всего проекта

### Этап A — зафиксировать baseline и владельцев
- Проверить завершение текущего CI/campaign run до push новых коммитов, если workflow отменяет предыдущий run при новом push.
- Инвентаризировать все WorldForge tick handlers, scheduled tasks, Rust JNI calls и повторяющиеся доменные проходы.
- Создать Compute Ownership Registry и Mod Optimization & Compatibility Inventory.
- Привязать каждую проблему к `KNOWN_ISSUES.md`.

### Этап B — безопасный asynchronous execution
- Ввести Rust worker scheduler и Java-side request/result queues.
- На серверном потоке только собирать immutable snapshot и применять готовые результаты.
- Добавить revision fence, single-flight по operation key, backpressure, shutdown и error handling.
- Не переносить Minecraft API в worker threads.

### Этап C — первая сквозная миграция: emergence и население
- Разделить Rust catch-up на возобновляемые детерминированные units.
- Перенести тяжёлый advance/decide с server thread в background compute.
- Разбить `syncEmergentPeople` на идемпотентные пакеты: Character, Origins, связи и дальнейшие стадии.
- Сохранить канонический registry, stable UUID, порядок событий и полную целевую численность.
- Удалить повторные full scans, когда их заменяют корректные revision/index/dirty checks.

### Этап D — следующие домены по профилю
- Потребности/профессии/экономика;
- торговля/маршруты/логистика;
- политика/династии/дипломатия;
- RTS/армии/снабжение/массовые бои;
- path planning и settlement task planning.

Каждый домен переносится отдельно: parity → cutover → отключение старого production calculation → регрессионные тесты.

### Этап E — ABI и память
- После стабильной async-модели сравнить JSON и binary/DirectByteBuffer.
- Переходить на compact arrays/SoA/data-oriented structures только там, где профиль доказывает выигрыш.
- Не менять одновременно несколько архитектурных переменных.

### Этап F — интеграция модов и долгосрочные оптимизации
- Проверить совместимость с фактическими оптимизаторами Forge/Minecraft.
- Исключить повторные scheduler/thread pools, tick hooks, кэши и path planners.
- Провести долгую кампанию, save/reload, обычный мир и multiplayer regression.

## 11. Тестовые и приёмочные критерии

Изменение не считается завершённым, пока не проверено:

- Rust unit/integration tests и Java logic tests;
- Windows x64 Forge build и native load;
- Linux native build;
- совместный Forge server boot;
- одинаковый seed: parity результатов до/после миграции;
- отсутствие двойных событий, двойных проводок, повторных Character/Origins;
- save → stop → reload → продолжение без потери cursor/queue/identity;
- отсутствие устаревшего результата при изменении input revision;
- bounded queue/backpressure и отсутствие silent drop;
- ordinary world regression без запуска кампании;
- полная автономная кампания без Watchdog/OOM и без уменьшения её объёма;
- проверка физического Minecraft мира и стратегической модели в обе стороны;
- compatibility matrix с реально установленными модами.

CI green подтверждает только выполненные в нём проверки. Не объявлять кампанию, multiplayer или обычный мир проверенными, если соответствующий тест не запускался.

## 12. Правила ведения работы между чатами

В начале продолжения работы:
1. Открыть этот документ и `docs/testing/KNOWN_ISSUES.md`.
2. Проверить актуальную ветку, HEAD commit, незавершённые CI runs и статус кампании.
3. Проверить текущий Compute Ownership Registry и Mod Optimization & Compatibility Inventory.
4. Не повторять уже внедрённую функцию и не создавать новый аналог без доказанной причины.
5. Перед изменением домена найти все реализации этой операции в Java, Rust и модах.
6. После реализации обновить документ/реестр, KNOWN_ISSUES, тесты и CI evidence.
7. Не трогать `main`, не запускать локальный Minecraft/сервер и не выпускать релизы без прямого разрешения пользователя.
8. Не пушить изменения, если это отменит критически важный текущий CI run, пока не сохранён его результат, кроме случая, когда пользователь явно попросил поступить иначе.

**Короткая формула проекта:** один расчёт — один владелец; Rust считает; Java безопасно применяет к Minecraft; моды согласованы; очереди сохраняют работу; оптимизация не отнимает механику и не дублирует чужую работу.

## 13. Актуальные рабочие реестры (2026-11-14)

Фактическое владение операциями и аудит пересечений ведутся отдельно:

- `docs/architecture/COMPUTE_OWNERSHIP_REGISTRY.md` — исходно проверенные operation keys, текущие/целевые владельцы, Java execution boundaries, статус миграции и первичный реестр внешних оптимизаций.
- `docs/testing/KNOWN_ISSUES.md` — подтверждённые дефекты, evidence, исправления и критерии закрытия.

**Важно:** целевая матрица этого документа не означает, что перенос уже завершён. При расхождении текущий production owner указывается в Compute Ownership Registry; переключение разрешено только после parity и acceptance gates. Реестр от 2026-11-14 пока неполон по сторонним runtime-модам и должен уточняться по фактическому modpack, loader/version и исходникам всех addon-подсистем.

`WF-RT-0020` отслеживает асинхронную миграцию WorldSim. Первая реализация scheduler и lifecycle fence уже находится в исходниках; CI, campaign regression и общий cross-domain mutation revision ещё не подтверждены.



Дополнительное правило для накопительных read-only проекций: нормальный поток новых событий должен использовать инкрементальное добавление, а не повторную сортировку/пересборку всей истории. Поздние факты сохраняют хронологическую семантику отдельным упорядоченным путём. Для ограниченной истории удаление префикса должно быть амортизированным, а не сдвигать весь ArrayList при каждом событии. Оптимизация не меняет канонический EventLog, глубину истории или её содержание и не создаёт второй журнал. Реализация отслеживается в WF-RT-0022.

Следующий обязательный freshness gate — общий mutation revision/vector авторитетных доменов. Day token WorldSim не доказывает согласованность Character/Origins/Realm/Settlement/Economy и других входов во время асинхронного расчёта. Расширять канонические write APIs, не создавать параллельные shadow counters в WorldSim. Отслеживается в WF-RT-0023.


### Масштабирование и конечные ресурсы

Отсутствие искусственного потолка сущностей не означает обещание бесконечной производительности на одном сервере. Архитектура должна масштабироваться по CPU/RAM и, в отдельном будущем этапе, по нескольким узлам. До появления revision fences, durable apply receipts и deterministic partition/reduce нельзя превращать текущий single-flight scheduler в произвольный пул параллельных writers. Подробный контракт профилей single-player/co-op/large-server и будущего multi-process ownership находится в `docs/architecture/WORLDSIM_SCALE_AND_BATTLE_CONTRACT.md`.


### WF-RT-0023 implementation note

A shared `DomainMutationRevisions` coordinator has been introduced in WorldForge Core. It supports domain lanes and commit-after-success mutation scopes; canonical EventLog writes are the first integrated lane. This is a foundation, not a complete global freshness guarantee. Character/Origins, Realm/Politics, Settlement, Treasury/Trade, Army/War and Inventory/Ownership writers remain to be audited and wired before WorldSim can use the vector as an apply fence.


### Character revision integration status

The shared `CHARACTERS` lane is now advanced by canonical `CharacterRegistry` lifecycle publication, restore, entity binding changes and calendar-derived age/life-stage updates. The legacy registry revision remains a membership/identity counter. This integration is post-write invalidation for current server-thread-owned paths; it is not yet a complete cross-thread mutation fence because direct mutable Character/props writers in addons remain under audit. Do not enable WorldSim global revision-based apply rejection until all such writers are scoped and covered by tests.
