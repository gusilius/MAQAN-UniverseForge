# UniverseForge — реестр проблем тестирования

Полные логи и диагностические пакеты каждого запуска хранятся в GitHub Actions Artifacts; сюда переносится краткая карточка проблемы и ссылка на запуск.

## Правила

- Не выдавать гипотезу за установленную причину.
- Каждой проблеме назначать ID WF-RT-NNNN, указывать подсистему, воспроизводимость, влияние, доказательства, исправление и результат повторного теста.
- Закрывать проблему только после повторного теста того же сценария и проверки отсутствия регрессии в обычном игровом мире.
- Тестовый сервер только собирает отчёты; исходники автоматически не меняются.
- Не снижать критерии кампании ради PASS; сохранять полный объём симуляции.

## Открытые записи

### WF-RT-0001 — блокировка Server thread при автономной кампании

- **Статус:** подтверждён повторный Watchdog; точная причина пока не установлена.
- **Подсистемы:** wf-worldsim ↔ wf-people ↔ wf-origins, материализация населения.
- **Первое наблюдение:** [CI run 43522418982](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43522418982); повтор: [CI run 43525730168](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43525730168).
- **Симптом:** после принятия команды кампании сервер завершился по Watchdog через 666 секунд; снижение ускорения с 8400 до 1200 не устранило зависание. Все сборочные, логические, нативные и совместные startup-проверки перед кампанией прошли.
- **Участок для проверки:** syncEmergentPeople(...) синхронно создаёт жителей до целевой численности в цикле while и затем обеспечивает Origins-записи для каждого жителя.
- **Гипотеза:** блокировка/чрезмерная длительность работы Server thread в одной из кампанийных стадий. Проверка syncEmergentPeople остаётся приоритетной, но конкретный стек Server thread в артефакт run 43525730168 не попал: текущий диагностический сборщик сохранял server.log, но не копировал crash-reports. Поэтому нельзя честно назначить виновную функцию.
- **Временная мера:** коммит 80805614ad1ac0772b34bf9cd6dfc17691062b66 уменьшил ускорение кампании с 8400 до 1200 игровых тиков на серверный тик.
- **Следующий шаг:** сохранить crash-reports и периодические JVM Thread.print дампы во время следующего прогона; по повторяющемуся стеку определить горячий участок и только затем внедрять пакетную/инкрементальную обработку.
- **Критерий закрытия:** полный четырёхпоколенный прогон без Watchdog, полные канонические жители и Origins-записи, обычная загрузка мира не запускает кампанию.

### WF-RT-0002 — повторная загрузка чанка из ChunkEvent.Load

- **Статус:** исправление внесено; ожидает полного Windows Forge CI и повторной кампании.
- **Подсистемы:** `wf-settlements` / `VanillaVillageAdapter`, интеграция с `wf-worldsim`.
- **Доказательство:** crash report из [CI run 43525730168](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43525730168), Watchdog stack: `WorldSimMod.forceCampaignSettlementChunks:578` → `VanillaVillageAdapter.onChunkLoad:57` → `reconcileInfrastructureChunk:196` → `adoptInfrastructureChunk:209` → `ServerChunkCache.getChunk`.
- **Причина:** обработчик `ChunkEvent.Load` синхронно запускал инфраструктурное сканирование чанка, пока `ServerChunkCache` ещё интегрировал этот же чанк. Внутри сканирования вызов `Level.getHeight` повторно запрашивал чанк через `getChunk`, блокируя главный поток ожиданием самого себя.
- **Исправление:** обработчик теперь только ставит позицию чанка в очередь. Очередь обрабатывается на последующих `ServerTickEvent.END`, максимум два уже загруженных чанка за тик. Немедленный обход соседних чанков при обнаружении деревни удалён; периодическая синхронизация жителей и уже загруженной инфраструктуры сохранена.
- **Критерий закрытия:** кампания проходит этап физической материализации без Watchdog; vanilla village инфраструктура продолжает связываться с общей моделью; обычный мир проходит smoke-тест.


### WF-RT-0003 — квадратично дорогая проверка журнала казначейства при каждом чтении ресурса

- **Статус:** исправление внесено; ожидает Windows Forge CI и повторной кампании.
- **Подсистема:** `wf-settlements` ↔ `wfmod TreasuryLedger`.
- **Доказательство:** crash report и JVM thread dump из [CI run 43529231720](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43529231720): Server thread провёл не менее 60 секунд в `Settlement.amount:246`, вызываемом из `eat()` и `economy()`; горячий стек — `journal().stream().anyMatch(...)`.
- **Причина:** `Settlement.amount(resource)` каждый раз линейно сканировал весь глобальный append-only TreasuryLedger journal в поиске одного дебета `LOGISTICS/army-field-rations`. Этот метод вызывается многократно из каждого экономического действия, поэтому рост журнала превращал обычный шаг поселения в повторяющиеся полные проходы по истории всех финансовых операций мира.
- **Исправление:** `TreasuryLedger` теперь поддерживает индекс аккаунтов, имеющих такой дебет; индекс обновляется при записи и восстанавливается при загрузке сохранённого журнала. `Settlement.amount()` выполняет O(1) проверку вместо stream scan. Формат сохранения не меняется.
- **Проверки:** добавлены тесты на добавление записи, изоляцию счёта и восстановление индекса из JSON.
- **Критерий закрытия:** тесты и полная кампания проходят; серверный тик больше не сканирует весь финансовый журнал для каждого чтения ресурса.
