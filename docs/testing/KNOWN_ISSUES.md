# UniverseForge — реестр проблем тестирования

Полные логи и диагностические пакеты каждого запуска хранятся в GitHub Actions Artifacts; сюда переносится краткая карточка проблемы и ссылка на запуск.

## Правила

- Не выдавать гипотезу за установленную причину.
- Каждой проблеме назначать ID WF-RT-NNNN, указывать подсистему, воспроизводимость, влияние, доказательства, исправление и результат повторного теста.
- Закрывать проблему только после повторного теста того же сценария и проверки отсутствия регрессии в обычном игровом мире.
- Тестовый сервер только собирает отчёты; исходники автоматически не меняются.
- Не снижать критерии кампании ради PASS; сохранять полный объём симуляции.

## Открытые записи

### WF-RT-0001 — блокировка Server thread при автономной кампании

- **Статус:** подтверждён повторный Watchdog; точная причина пока не установлена.
- **Подсистемы:** wf-worldsim ↔ wf-people ↔ wf-origins, материализация населения.
- **Первое наблюдение:** [CI run 43522418982](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43522418982); повтор: [CI run 43525730168](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43525730168).
- **Симптом:** после принятия команды кампании сервер завершился по Watchdog через 666 секунд; снижение ускорения с 8400 до 1200 не устранило зависание. Все сборочные, логические, нативные и совместные startup-проверки перед кампанией прошли.
- **Участок для проверки:** syncEmergentPeople(...) синхронно создаёт жителей до целевой численности в цикле while и затем обеспечивает Origins-записи для каждого жителя.
- **Гипотеза:** блокировка/чрезмерная длительность работы Server thread в одной из кампанийных стадий. Проверка syncEmergentPeople остаётся приоритетной, но конкретный стек Server thread в артефакт run 43525730168 не попал: текущий диагностический сборщик сохранял server.log, но не копировал crash-reports. Поэтому нельзя честно назначить виновную функцию.
- **Временная мера:** коммит 80805614ad1ac0772b34bf9cd6dfc17691062b66 уменьшил ускорение кампании с 8400 до 1200 игровых тиков на серверный тик.
- **Следующий шаг:** сохранить crash-reports и периодические JVM Thread.print дампы во время следующего прогона; по повторяющемуся стеку определить горячий участок и только затем внедрять пакетную/инкрементальную обработку.
- **Критерий закрытия:** полный четырёхпоколенный прогон без Watchdog, полные канонические жители и Origins-записи, обычная загрузка мира не запускает кампанию.

### WF-RT-0002 — повторная загрузка чанка из ChunkEvent.Load

- **Статус:** исправление внесено; ожидает полного Windows Forge CI и повторной кампании.
- **Подсистемы:** `wf-settlements` / `VanillaVillageAdapter`, интеграция с `wf-worldsim`.
- **Доказательство:** crash report из [CI run 43525730168](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43525730168), Watchdog stack: `WorldSimMod.forceCampaignSettlementChunks:578` → `VanillaVillageAdapter.onChunkLoad:57` → `reconcileInfrastructureChunk:196` → `adoptInfrastructureChunk:209` → `ServerChunkCache.getChunk`.
- **Причина:** обработчик `ChunkEvent.Load` синхронно запускал инфраструктурное сканирование чанка, пока `ServerChunkCache` ещё интегрировал этот же чанк. Внутри сканирования вызов `Level.getHeight` повторно запрашивал чанк через `getChunk`, блокируя главный поток ожиданием самого себя.
- **Исправление:** обработчик теперь только ставит позицию чанка в очередь. Очередь обрабатывается на последующих `ServerTickEvent.END`, максимум два уже загруженных чанка за тик. Немедленный обход соседних чанков при обнаружении деревни удалён; периодическая синхронизация жителей и уже загруженной инфраструктуры сохранена.
- **Критерий закрытия:** кампания проходит этап физической материализации без Watchdog; vanilla village инфраструктура продолжает связываться с общей моделью; обычный мир проходит smoke-тест.


### WF-RT-0003 — квадратично дорогая проверка журнала казначейства при каждом чтении ресурса

- **Статус:** исправление внесено; ожидает Windows Forge CI и повторной кампании.
- **Подсистема:** `wf-settlements` ↔ `wfmod TreasuryLedger`.
- **Доказательство:** crash report и JVM thread dump из [CI run 43529231720](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43529231720): Server thread провёл не менее 60 секунд в `Settlement.amount:246`, вызываемом из `eat()` и `economy()`; горячий стек — `journal().stream().anyMatch(...)`.
- **Причина:** `Settlement.amount(resource)` каждый раз линейно сканировал весь глобальный append-only TreasuryLedger journal в поиске одного дебета `LOGISTICS/army-field-rations`. Этот метод вызывается многократно из каждого экономического действия, поэтому рост журнала превращал обычный шаг поселения в повторяющиеся полные проходы по истории всех финансовых операций мира.
- **Исправление:** `TreasuryLedger` теперь поддерживает индекс аккаунтов, имеющих такой дебет; индекс обновляется при записи и восстанавливается при загрузке сохранённого журнала. `Settlement.amount()` выполняет O(1) проверку вместо stream scan. Формат сохранения не меняется.
- **Проверки:** добавлены тесты на добавление записи, изоляцию счёта и восстановление индекса из JSON.
- **Критерий закрытия:** тесты и полная кампания проходят; серверный тик больше не сканирует весь финансовый журнал для каждого чтения ресурса.


### WF-RT-0004 — исчерпание Java heap при сохранении растущего казначейского журнала

- **Статус:** исправление внесено; ожидает Windows Forge CI и повторной полной кампании.
- **Подсистема:** `wfmod TreasuryLedger` / сохранение мира.
- **Доказательство:** [CI run 43532590865](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43532590865), артефакт `maqan-planetos-autonomous-campaign`, crash report `crash-2026-11-14_00.51.06-server.txt`. Стек: `TreasuryLedger.toJson:249` → `WorldForgeMod.saveTreasury:170` → `WorldForgeMod.onTreasuryTick:257`; ошибка `OutOfMemoryError: Java heap space` в `Json.quote` при сборке общей строки.
- **Причина:** финансовый журнал сохраняется целиком и растёт по мере работы мира. Старый сериализатор одновременно строил массив объектов для всех записей и затем ещё одну общую JSON-строку. Пиковое потребление памяти становилось кратно больше размера самого журнала.
- **Исправление:** добавлен потоковый `TreasuryLedger.writeJson(Writer)`: записи кодируются по одной непосредственно в выходной поток, без промежуточного списка всех JSON-объектов и без единой гигантской строки. Автосохранение пишет через `BufferedWriter` во временный файл и затем выполняет атомарную замену. Формат `wf-treasury-ledger/1`, полный журнал, последовательности и ключи идемпотентности сохранены; история не обрезается и не агрегируется.
- **Проверки:** добавлен стресс-тест на 12 000 финансовых записей с потоковой сериализацией и восстановлением; ожидает CI.
- **Ограничение исправления:** оно устраняет пиковые аллокации сериализатора, но не вводит архивирование/сегментацию истории. Время записи полного журнала остаётся пропорциональным его размеру и будет наблюдаться в повторной кампании.
- **Дополнительный сигнал того же запуска:** WorldSim логировал `realms=0 settlements=0 proposals=0 applied=0 rejected=0` при `day=23941`. Это отдельная открытая проблема генерации/подачи данных в стратегический симулятор; не считать её решённой данным изменением.
- **Критерий закрытия:** стресс-тест и полная кампания проходят без OOM/Watchdog; в отчёте есть ненулевые государства, поселения и жители, а журнал после перезапуска сохраняет баланс и идемпотентность.


### WF-RT-0005 — квадратичный обход населения при заполнении дворов emergent-государств

- **Статус:** исправление внесено; ожидает повторного Windows Forge CI и полной кампании.
- **Подсистемы:** `wf-worldsim.syncEmergentPolities` → `wf-people.Courts.ensure` → `CharacterRegistry.holders`.
- **Доказательство:** [CI run 43581857875](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43581857875), артефакт `maqan-planetos-autonomous-campaign` (ID 14110875701), crash report `crash-2026-11-14_10.36.16-server.txt). Watchdog stack: `CharacterRegistry.holders:329` → `Courts.ensure:40` → `WorldSimMod.syncEmergentPolities:1315`. Кампания зависла после ~39 минут; в этот момент WorldSim логировал `realms=0 settlements=0`.
- **Причина:** `Courts.ensure` вызывал `reg.holders(role, place)` для каждой пары роль/титул/государство. `holders` каждый раз проходил по всему реестру персонажей. С ростом населения и числа политических мест получалась работа порядка O(roles × places × population) на одном серверном потоке.
- **Исправление:** `Courts.ensure` теперь один раз строит счётчики живых назначений по ключу роль+место и множество занятых домов, затем выполняет заполнение по O(1) запросам. Учитывает назначения, созданные в рамках текущего прохода. Генерация персонажей, семей, ролей и детерминированные seed-значения не отключаются и не урезаются.
- **Дополнительная оптимизация:** устранено повторное полное сканирование реестра домов для каждого нового правителя; набор занятых домов поддерживается в ходе одного прохода.
- **Проверки:** добавлена проверка идемпотентности повторного `Courts.ensure` на общей карте; ожидает CI.
- **Критерий закрытия:** повторная кампания проходит синхронизацию emergent-политий без долгого тика; должности и семейные записи остаются полными и без дубликатов.

### WF-RT-0006 — повторная сортировка глобальных идентичностей при каждом поиске наследника

- **Статус:** оптимизация внесена; ожидает тестов и наблюдения в кампании.
- **Подсистемы:** `wf-court.CourtSim.die` → `CharacterRegistry.kill` → `CharacterInventory.findHeir` → `CharacterAuthority.identities`.
- **Доказательство:** thread dump из того же [CI run 43581857875](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43581857875), `thread-dump-1794650871.txt`: серверный поток сортировал весь `CharacterAuthority.identities()` внутри `CharacterInventory.findHeir()` во время смерти персонажа и передачи наследства.
- **Причина:** `identities()` каждый вызов строил и сортировал новый список всех мировых персонажей, хотя состав реестров между такими запросами часто не менялся.
- **Исправление:** добавлен неизменяемый кеш отсортированного снимка идентичностей; сбрасывается только при изменении состава/ревизии зарегистрированных реестров или очистке authority.
- **Проверки:** добавлены тесты повторного использования снимка и его инвалидации после добавления персонажа.
- **Ограничение:** поиск дальнего родственника всё ещё может проходить по всем персонажам, если у умершего нет прямого наследника; этот fallback не удалён и требует отдельного профиля.
- **Критерий закрытия:** тесты кеша проходят; смерти и наследование не вызывают повторной сортировки всего мира на каждом событии.

### WF-RT-0007 — высокая стоимость ежедневного обновления потребностей населения (наблюдение)

- **Статус:** наблюдение, первопричина не установлена; не объявлять дефектом до повторного профиля.
- **Подсистема:** `wf-people.PopulationSimulation.advance`.
- **Доказательство:** `thread-dump-1794650963.txt` того же запуска показывает серверный поток в `PopulationSimulation.changeNeed/setNeed` из `advance`.
- **Что известно:** ежедневный проход обходит всех персонажей и обновляет несколько потребностей, намерение и календарные свойства. Один снимок потока подтверждает активность этого пути, но не доказывает, что именно он вызвал финальный 60-секундный тик.
- **Следующий шаг:** после исправления WF-RT-0005 повторить кампанию и сравнить несколько периодических дампов; оценить долю CPU, размер населения и число обновляемых записей. Не отключать потребности и повседневную симуляцию как обходной путь.
- **Критерий решения:** подтвердить или снять проблему по повторяемым профилям; при подтверждении — инкрементальное обновление без потери нужд, возрастов и намерений.


### WF-RT-0008 — ошибка компиляции разделителя ключа индекса двора

- **Статус:** исправлено следующим коммитом; повторная сборка ожидает CI.
- **Подсистема:** `wf-people.Courts`.
- **Доказательство:** [CI run 43586672748](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43586672748), шаг `Compile and run WorldForge logic tests`: Java compiler сообщил `unclosed character literal` в `Courts.java:66` на строке с попыткой использовать escaped NUL-разделитель.
- **Причина:** при формировании исходного Java-файла был записан неверно экранированный символьный литерал `'\\u0000'`; Java трактует его как некорректный литерал.
- **Исправление:** разделитель заменён на обычный строковый `"#"` в ключе роль/место. Оба поля являются идентификаторами ролей и мест, не содержащими этот разделитель.
- **Результат:** коммит `c868659bc6bca4bf169a73db3003e1deeebca04a` содержит исправление. Ожидается проверка компиляции и логических тестов на следующем запуске.


### WF-RT-0009 — квадратичная материализация emergent-населения и связывание работников

- **Статус:** исправление внесено; ожидает Windows logic tests, полной Forge-кампании и сравнения диагностик.
- **Подсистема:** `wf-worldsim.syncEmergentPeople` / `syncEmergentPolities` ↔ канонический `wf-people.CharacterRegistry`.
- **Основание:** аудит кода после Watchdog в [CI run 43581857875](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43581857875). Для каждой группы прежний код заново обходил весь реестр; затем при создании поселения повторно сканировал его для UUID, а после этого отдельно искал каждого жителя полным проходом. Для каждой политии снова сканировалось население и отдельно искался прежний правитель.
- **Причина:** вложенные линейные запросы превращали материализацию в O(группы × население + жители поселений × население + политии × население).
- **Исправление:** добавлен краткоживущий `EmergentPopulationIndex`: один проход по каноническому реестру строит группы живых жителей по band ID, поиск по global UUID и список всех emergence-персонажей, включая умерших. Индекс обновляется при создании новых канонических персонажей и не является параллельным хранилищем идентичности. Обе синхронизации используют его вместо повторных полных сканирований.
- **Дополнительное исправление:** выбор взрослых родителей кешируется на время материализации группы; полный обход уже созданных жителей при каждом рождении устранён.
- **Проверки:** добавлен `EmergentPopulationIndexTest` для изоляции групп, учёта умерших, UUID lookup и добавления новых канонических жителей в текущий индекс.
- **Критерий закрытия:** Windows logic tests проходят; полная кампания проходит материализацию населения, физические поселения и политическую синхронизацию без Watchdog; число жителей и UUID-связи совпадают с каноническим реестром.


### WF-RT-0010 — высокая стоимость ежедневного обновления потребностей канонического населения

- **Статус:** оптимизация внесена; ожидает Windows logic tests и повторного Forge campaign profiling. Не объявлять первопричиной Watchdog без совпадающего crash stack.
- **Подсистема:** `wf-people.PopulationSimulation.advance` / `PeopleMod.onTick`.
- **Доказательство:** несколько периодических thread dump из [CI run 43581857875](https://github.com/gusilius/MAQAN-UniverseForge/actions/runs/43581857875) показывают Server thread внутри `PopulationSimulation.advance`; в одном снимке CPU time потока достиг 298 секунд за ~769 секунд работы. Финальный crash report этого запуска указывает на `Courts.ensure`, поэтому данный участок — подтверждённый горячий путь, но не доказанная причина финального 60-секундного зависания.
- **Причина:** для каждого живого персонажа старый цикл пять раз вызывал `changeNeed`, каждый раз повторно получая вложенную карту и создавая строковый ключ через `Need.name().toLowerCase`; затем `updateIntent/decide` снова получали ту же карту и повторно вычисляли ключи.
- **Исправление:** ключи Need/Intent теперь заданы в enum; один проход по персонажу получает карту потребностей один раз, применяет все дневные изменения и рассчитывает intent на том же снимке. Дневной дрейф вычисляется один раз на весь registry. Добавлено насыщающее сложение счётчика прожитых дней.
- **Сохранённая семантика:** все шесть потребностей, приоритеты intent, возраст, стадии жизни, профессии, военные обязанности и календарный elapsedDays остаются активны. Ничего не отключается и не пропускается.
- **Проверки:** добавлен тест трёхдневного пакетного обновления с точными ожидаемыми значениями всех потребностей и simulated_days.
- **Критерий закрытия:** логические тесты проходят; в периодических дампах длительной кампании доля CPU этого пути снижается, а состояние потребностей/intent совпадает с эталонной пошаговой моделью.


### WF-RT-0011 — генерация должностных персонажей на тысячах ничейных титулов

- **Статус:** исправление внесено; ожидает Windows logic tests и повторного полного Forge-прогона.
- **Подсистема:** `wf-worldsim.syncEmergentPolities` → `wf-people.Courts.ensure` → `TitleData`.
- **Основание:** в geography-only кампании PeopleMod намеренно пропускает начальное заполнение authored дворов, но `WorldSimMod.syncEmergentPolities` затем безусловно вызывает `Courts.ensure`. Аудит показал, что прежний цикл брал все `d.allTitles()` для county/barony-ролей независимо от того, владеет ли какой-либо realm этими титулами. В такой карте тысячи пустых титулов превращались в несуществующую политическую структуру и лишнее население; тот же вызов присутствовал в Watchdog-стеке WF-RT-0005.
- **Причина:** `Courts.ensure` трактовал все географические титулы как активные феодальные места, хотя незанятый титул без государства не должен иметь кастеляна/жителей двора.
- **Исправление:** один раз строится набор титулов, лежащих в родительской цепочке реально принадлежащих realm провинций. County/barony роли создаются только для этих титулов. Роли уровня realm продолжают создаваться для emergent и authored государств; генерация населения и семей не отключается.
- **Проверки:** добавлен тест, который очищает владение провинциями, запускает Courts.ensure и подтверждает отсутствие title-office персонажей при сохранении правителей/советов существующих realm-проекций.
- **Критерий закрытия:** Windows logic tests проходят; geography-only кампания не создаёт феодальные дворы на ничейной карте; после реального присвоения провинций государству соответствующие county/barony должности заполняются.
