# Этап XI — единое управление RTS и НПС

## Управление
- `R` — войти/выйти из командного режима.
- ЛКМ — выбрать юнита; протянуть ЛКМ — рамка; Shift — добавить/убрать; двойной клик — выбрать видимый тип.
- `Ctrl+1..9` — сохранить группу; `1..9` — вызвать; Shift+цифра — добавить к выбору.
- ПКМ по земле — перемещение; Ctrl+ПКМ — атака по пути; Shift+ПКМ — добавить приказ в очередь.
- ПКМ по врагу — прямая атака; гражданские рабочие не получают приказ прямой атаки.
- `Z` — стоп; `X` — удерживать; `C` — следующий строй; `M` — следующая боевая стойка.
- `P` — патруль между текущей позицией отряда и точкой под курсором; Shift+P добавляет приказ в очередь.
- `V` — назначить выбранного персонажа командиром его отряда; Ctrl+V — снять командиров.
- `F` — собрать выбранных солдат в отряд; Delete — освободить выбранных рабочих.
- `B` — меню строительства; Shift при размещении сохраняет выбранный чертёж для следующего размещения.
- `Space` — фокус на выбранных; WASD/края экрана — перемещение камеры; колесо — высота; средняя кнопка — вращение; Tab — вид.

## Единый выбор и инспектор
Командный режим принимает только солдат текущего владельца и физических рабочих поселений, владелец которых совпадает с UUID игрока. Данные владельца и личности рабочего синхронизируются через entity data. У солдата синхронизируются Character ID и боевой опыт.

Инспектор показывает имя, профессию/роль, здоровье, мораль, боевой опыт, Character ID, отряд и состояние текущей работы. Клик по строке фокусирует камеру на выбранной единице.

## Очереди и патруль
- Очередь солдат использует сохранённую очередь приказов отряда.
- Очередь рабочего — до 16 точек маршрута; Shift+ПКМ добавляет точку. По достижении точки физический WFWorker активирует следующую.
- Очередь рабочего сохраняется в Settlement JSON и восстанавливается при загрузке.
- Стоп/удержание очищает очередь рабочего.
- Патруль хранит исходную и конечную точки и чередует их; оба конца и состояние возврата сохраняются в JSON отрядов.

## Межмодульная оптимизация командной иерархии

В `wf-troops/ArmyHierarchy` добавлен обратный индекс `squadId -> corpsId`. Он не дублирует состав: список отрядов корпуса остаётся сохраняемым источником структуры, а индекс ускоряет поиск родительского корпуса для выбранного отряда. Переназначение, снятие, очистка отсутствующих отрядов и загрузка JSON синхронизируют индекс. Для старых дополнений, которые ещё меняют публичный список напрямую, оставлен путь совместимого восстановления индекса.

## Согласование приоритетов профессий

Матрица `wf-rts` больше не считает клиентскую карту источником истины: сохранённые значения читаются из `Worker.jobPrio`, а `wf-settlements/Settlement` остаётся владельцем правил и автоподбора. Команда `priority-work` записывает приоритет в Settlement; сервер проверяет диапазон 0..4, существование профессии и совместимость рабочего. Значения сериализуются в снимке поселения. При получении нового серверного снимка UI сбрасывает оптимистичные переопределения и показывает подтверждённые данные. Несовместимые ячейки матрицы заблокированы, массовое изменение столбца пропускает таких работников.

## Оптимизация сверки общего ресурсного журнала

В `wf-settlements/Settlement.amount` legacy stock mirror reconciliation больше не сканирует журнал казны при каждом чтении ресурса. Решение о необходимости миграционной сверки по-прежнему принимается один раз для загруженного снимка; поиск признака ранее выполненного армейского списания выполняется не более одного раза на ресурс и только если миграция действительно нужна. После этого чтение использует актуальный баланс общего TreasuryLedger. Добавлен регрессионный тест с повторными чтениями, проверяющий отсутствие повторных записей в журнал.

## Индексация физических тел канонических персонажей

`CharacterRegistry` теперь поддерживает обратный индекс `Minecraft Entity UUID -> Character ID`. Привязка нового тела и проверка уникальности выполняются через индекс, а не полным обходом реестра персонажей. Перепривязка body kind освобождает прежний UUID только если на него больше не ссылается другая привязка того же персонажа; точный unbind и смерть персонажа очищают индекс. При загрузке реестр атомарно восстанавливает индекс из проверенных `population.entity_bindings`; повторяющийся UUID между разными персонажами отклоняет весь снимок до замены действующего состояния. Это сохраняет Character как единственную личность, а Minecraft Entity — как заменяемое физическое тело.

## Единое владение задачами жителей

В `Worker` введён lease активной задачи с владельцами `NONE`, `LIFE`, `SETTLEMENT`, `MILITARY`, `PLAYER` и возрастающими приоритетами. Ручное управление игрока не может быть перехвачено военным/гражданским автопланировщиком; военный приказ не может быть отменён обычным назначением или сменой профессии. Повседневное действие и прямой маршрут игрока могут временно приостанавливать гражданскую работу, а после завершения возвращают сохранённые здание, точную профессию, ручное назначение носильщика либо параметры жизненного действия, если исходная задача ещё допустима. Приостановки хранятся стеком LIFO, поэтому последовательность «работа → сон/еда → военный приказ → прямое управление» корректно разворачивается в обратном порядке, не теряя исходное назначение. Стек ограничен восемью уровнями и сохраняется с обратной совместимостью односоставных снимков.

`Settlement.claimMilitaryTask/releaseMilitaryTask`, `claimLifeTask/releaseLifeTask` и `releasePlayerTask` образуют межмодульный контракт арбитража. Переход существующего Character из поселения в военную службу проходит через тот же арбитр: житель с активным прямым приказом игрока не может быть незаметно изъят. Отмена здания освобождает его task lease; автоматическое назначение выбирает только работников без активного владельца задачи. Состояние текущей и приостановленной задачи сохраняется в снимке поселения; legacy-снимки восстанавливают владельца по прежним authoritative-флагам, а orphaned leases очищаются.

Добавлены регрессионные сценарии для вложенной последовательности «стройка → повседневная жизнь → военный приказ → маршрут игрока» с сохранением/загрузкой между этапами, защиты активного player order при зачислении в армию, stale-order rejection и освобождения lease при отмене стройки. В `SettleMod.runLifeAI` ежедневные действия теперь получают и освобождают LIFE lease; завершение сна/еды/защиты восстанавливает прерванную работу. Это пока логические тесты в исходниках; их исполнение и runtime-интеграция не подтверждены.

## Проверки и ограничения

Все сетевые приказы повторно проверяются сервером: размер списка, уникальность идентификаторов, тип действия, координаты и целевые UUID. Клиентская видимость юнита не считается разрешением на управление — владелец проверяется на стороне сервера.
Логические тесты покрывают:
- очередь рабочего: добавление, последовательное выполнение, save/load, очистка и лимит;
- патруль: сохранение двух конечных точек и возврат между ними;
- существующие тесты выбора, групп, смешанных приказов, строя, морали, снабжения и командования.

Пока не реализованы: активная панель боевых способностей с cooldown/ресурсной стоимостью; полноценные геройские ветви навыков; единый граф задач «добыть → перенести → доставить → построить»; полноценная multiplayer/runtime-проверка. Эти пункты остаются блокерами принятия Этапа XI.
